# 好友代付技术设计

- 日期：2026-09-03
- 涉及项目：`yueji-backend`、`../yueji-web`
- 状态：已确认

## 1. 目标与前提

待付款订单可生成微信分享链接和海报，好友登录后使用自己的微信账户付款；购买人看到代付状态及时更新。订单履约、预约、营销和售后仍归订单购买人，退款原路退给实际付款人。

好友代付依赖真实微信小程序 JSAPI 支付。当前 `WechatPaymentDriver` 仍是未配置占位实现，因此本功能实施必须同时补齐微信支付下单、查单、关单、回调和退款能力。

首期只支持普通订单，不支持拼团订单代付。拼团另有成团截止时间和失败退款链路，待普通订单资金链路稳定后再单独接入。

## 2. 已确认规则

1. 订单购买人与实际付款人分别记录，代付不改变订单归属。
2. 同一订单允许多次支付尝试，但同一时刻最多一笔支付中。
3. 第一笔有效成功支付完成订单；异常迟到的其他成功支付自动原路退款。
4. 代付链接与订单付款期限一致，当前默认约 30 分钟。
5. 代付预览显示商品摘要和应付总额，不显示联系人、手机号和完整订单号。
6. 状态更新采用微信异步回调加页面可见期间每 2 秒轮询，不增加 WebSocket。
7. 代付好友的成功页不显示“去预约”；购买人的成功页继续显示。

## 3. 方案选择

采用“支付记录表示一次支付尝试”的方案：

- 一个订单可对应多条 `biz_payment`。
- `member_id` 继续表示订单购买人，`payer_member_id` 表示实际付款人。
- `biz_order.paid_payment_id` 指向真正完成订单的支付尝试。
- 数据库约束保证同一订单最多一条有效 `PENDING` 支付。
- 退款按支付记录处理，从而能够退回正确账户。

不复用并重置单条支付记录：微信商户订单号必须唯一且用于幂等，重置无法安全处理换人、超时和迟到回调。

不单独建设第二套代付支付系统：它会重复回调、退款、对账和异常补偿逻辑。

## 4. 代付展示状态

代付状态不单独持久化，由订单和当前支付尝试推导：

```text
WAITING ──好友发起支付──→ PAYING
   │                         │
   ├──订单超时取消──→ EXPIRED│
   └──购买人取消──→ CANCELLED│
                             ├──成功──→ PAID
                             └──失败/关单──→ WAITING
```

订单进入 `PAID`、`CANCELLED` 或 `REFUNDED` 后，所有分享入口立即成为终态。

## 5. 数据模型

### 5.1 `biz_order`

新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `paid_payment_id` | `bigint` 可空 | 真正完成订单的支付记录 ID |

`paid_payment_id` 增加外键和唯一索引；应用写入时还必须校验该支付记录的 `order_id` 与当前订单一致。历史 `PAID / VERIFIED / COMPLETED / REFUNDED` 订单按实际成功或已退款支付记录回填；未付款订单保持为空。

### 5.2 `biz_payment`

保留现有状态 `PENDING / SUCCESS / FAILED / REFUNDED`，新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `payer_member_id` | `bigint` | 实际调起支付的会员 |
| `prepay_id` | `varchar(64)` 可空 | 微信预支付会话 ID |
| `expire_time` | `datetime` 可空 | 当前支付尝试租约结束时间 |

索引调整：

- 删除 `uk_payment_order_id`，改为普通 `order_id` 索引。
- 增加付款人索引。
- 增加生成列 `active_order_id = CASE WHEN status = 0 AND is_deleted = 0 THEN order_id END` 及唯一索引，保证同一订单最多一条支付中记录。
- 历史数据把 `payer_member_id` 回填为 `member_id`。

`prepay_id` 必须持久化；重复进入支付页时可复用相同微信预支付单，并重新生成前端调起签名参数。

支付尝试租约与订单付款期限分开：订单分享仍在下单后约 30 分钟失效，每次支付尝试默认占用 5 分钟，`expire_time = min(当前时间 + 5 分钟, 订单付款截止时间)`。订单剩余不足微信允许的最短支付时间时不再创建尝试。该尝试的微信 `time_expire` 使用同一时间，超时后好友可在查单、关单完成后重新尝试。

### 5.3 `biz_refund`

- 删除 `order_id` 唯一索引。
- 增加 `payment_id` 唯一索引。
- 保留 `order_id` 普通索引供业务查询。

这样既能退款真正完成订单的支付，也能为极端情况下的额外成功支付创建自动退款。

### 5.4 `biz_proxy_pay_share`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `order_id` | `bigint` | 待付款订单 |
| `owner_member_id` | `bigint` | 订单购买人 |
| `token_hash` | `char(64)` | 128 位随机令牌的 SHA-256 |
| `expires_at` | `datetime` | 与订单付款截止时间一致 |

只保存分享凭证，不保存冗余状态。`token_hash` 唯一，`order_id` 增加普通索引。允许同一订单生成多个仍有效的分享入口，全部由订单终态统一关闭。

令牌使用 `randomBytes(16).toString("base64url")`，长度适合放入微信小程序码 `scene`。

## 6. 支付尝试与并发

所有自付和代付统一经过一段内部支付准备逻辑：

1. 写锁订单并校验仍为 `UNPAID`、未超过付款期限。
2. 查找并写锁该订单的有效 `PENDING` 支付。
3. 同一付款人重复请求时复用；不同付款人请求时返回“已有好友支付中”。
4. 支付尝试超时后先向微信查单：
   - 已成功：按成功流程处理。
   - 明确未支付：成功关单后标为 `FAILED`，再创建新支付编号。
   - 查询或关单结果不确定：保留 `PENDING`，拒绝创建第二笔。
5. 新支付记录同时保存订单购买人和实际付款人。

购买人自付也遵守相同互斥规则，避免自付与代付同时扣款。

支付创建、回调、主动查单和退款统一使用 `订单 → 支付 → 退款` 的加锁顺序。按支付编号进入的流程先无锁读取 `order_id`，进入事务后再按该顺序加锁并重新校验，避免与创建支付发生锁顺序反转。

微信下单、查单、关单和退款都是外部网络调用，绝不在持有数据库锁的事务中执行。统一拆为“短事务读取并确定候选 → 事务外调用微信 → 新短事务重新加锁并应用结果”；数据库唯一索引负责阻止释放锁期间出现第二条 `PENDING`。

若微信下单已经成功，但进程在保存 `prepay_id` 前退出，重试时不得盲目再次下单。本地 `prepay_id` 为空时先查微信：已支付则正常落账；`NOTPAY` 时先关单，再把旧尝试改为 `FAILED` 并使用新 `paymentNo` 创建；结果不确定则保持 `PENDING`，禁止第二笔支付。

## 7. 支付成功与迟到支付

支付回调处理：

1. 验证微信平台签名并使用 API v3 密钥解密资源。
2. 校验 `appid`、`mchid`、商户支付号、金额和微信支付号。
3. 先无锁定位订单，事务内依次写锁订单和支付记录，并重新校验二者关系。
4. 当前订单仍为 `UNPAID` 且 `paid_payment_id` 为空时：
   - 支付记录改为 `SUCCESS`。
   - 写入 `paid_payment_id`。
   - 使用现有订单状态转换进入 `PAID`。
5. 当前订单已经被另一笔支付完成时：
   - 本支付记录仍如实记为 `SUCCESS`。
   - 创建自动退款意图并在事务提交后调用微信退款。
6. 重复回调返回成功，不重复推进订单、发放权益或退款。

补偿任务除现有 `PENDING` 查单外，还需扫描“成功但不是订单 `paid_payment_id` 且尚未退款”的记录，确保进程退出后仍会自动退款。

退款结果必须区分主支付和额外支付：只有 `refund.payment_id === order.paid_payment_id` 时才允许把订单推进为 `REFUNDED`；额外成功支付的自动退款只修改对应支付与退款记录，绝不能把正常的 `PAID / VERIFIED / COMPLETED` 订单改为退款。取消订单后的迟到支付可自动退款，并沿用现有 `CANCELLED → REFUNDED` 语义。

订单主动取消或超时取消后，在事务提交后立即尝试关闭对应 `PENDING` 微信订单；迟到成功自动退款只是异常兜底。补偿任务同时扫描过期支付尝试并主动查单、关单，避免长期停留在 `PENDING`。

### 7.1 退款状态与补偿规则

- `PROCESSING`：先查单，只有微信明确返回退款单不存在时，才使用原 `refundNo` 和原始参数幂等重提。
- `SUCCESS`：用户资金已到账；完整校验支付号、微信支付流水、退款号、微信退款流水、原支付金额、退款金额和币种后落账，且不得被迟到状态降级。
- `FAILED`：本次渠道申请明确失败。普通主订单重新开放履约且不自动退款；额外扣款或取消后的迟到支付在退避后更换 `refundNo` 自动重试。
- `CLOSED`：更换 `refundNo` 后重试，旧号保留用于迟到通知和审计。
- `ABNORMAL`：禁止同号重提，只持续查单并在微信商户平台人工处理。若异常退款退回商户银行账户，仍保持人工待办，不视为已退给用户。

预约、核销和送礼只检查订单 `paid_payment_id` 对应退款的 `PROCESSING / CLOSED / ABNORMAL`；额外支付的退款不阻断正常订单履约。退款 `SUCCESS` 是资金事实，即使本地履约状态冲突也必须保存支付和退款结果并告警，不能回滚渠道事实。

## 8. 微信支付驱动

`PaymentCreateRequest` 增加：

- `payerOpenid`
- `expireAt`

`PaymentDriver` 增加 `close(paymentNo)`；其他接口继续使用 `paymentNo`、`refundNo` 作为幂等键。

`WechatPaymentDriver` 使用现有 Axios 和 Node.js `crypto` 实现：

- API v3 请求签名和平台证书验签。
- 小程序 JSAPI 下单。
- 按商户订单号查单。
- 关闭订单。
- 申请退款与查询退款。
- 回调 AES-256-GCM 解密。
- 根据持久化 `prepay_id` 生成 `timeStamp / nonceStr / package / signType / paySign`。

回调路由必须取得原始请求体、绕过会员鉴权和统一响应包装。应用启动时校验必需配置；开发环境使用 mock 驱动时不要求微信证书。

所有微信 API 响应和回调均按响应头中的平台证书序列号或公钥 ID 选择验证密钥；支持并存新旧密钥完成轮换。未知密钥、验签失败、解密失败或金额不一致一律 fail closed，不推进本地状态。签名、验签和解密使用微信官方测试向量验证。

必需配置：

- 小程序 AppID。
- 微信支付商户号。
- API v3 密钥。
- 商户私钥及证书序列号。
- 微信平台证书或平台公钥。
- 公网 HTTPS 支付与退款回调地址。

## 9. 服务端接口

统一前缀 `/api/v1`：

| 方法 | 路径 | 鉴权 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/app/proxy-pay/share` | 订单购买人 | 创建分享 |
| `POST` | `/app/proxy-pay/preview` | 公开、限流 | 安全预览 |
| `POST` | `/app/proxy-pay/payment` | 会员 | 创建或复用代付支付 |
| `POST` | `/app/proxy-pay/status` | 公开、限流 | 查询派生状态 |
| `POST` | `/app/proxy-pay/poster-code` | 订单购买人 | 获取小程序码图片 |
| `POST` | `/app/payment/wechat/notify` | 微信签名 | 支付结果回调 |
| `POST` | `/app/payment/wechat/refund-notify` | 微信签名 | 退款结果回调 |

公开接口令牌放请求体。返回内容不包含联系人、手机号、完整订单号、购买人 ID 或支付流水详情。

实际付款人可查询自己的支付尝试和调起参数；订单购买人只通过订单或代付状态接口查看结果，不能读取好友的支付流水及 OpenID。开发环境的 mock 确认同样按 `payer_member_id` 鉴权。

小程序码接口返回 PNG 二进制并绕过统一 JSON 包装。微信 `access_token` 复用现有 Redis 缓存逻辑；把 `MemberAuthService` 内现有实现提取为两个调用方共用的最小服务，不建立第二套缓存。

## 10. 小程序页面

- 实现现有 `/pages-sub/order/proxy-pay/index` 页面，覆盖分享发起、好友预览、支付中和结果状态。
- 订单卡片仅在 `UNPAID` 且仍在付款期限内显示“好友代付”。
- 好友打开分享后先看安全预览；点击支付时要求登录，并使用当前会员 OpenID 调起 `uni.requestPayment`。
- `onShow` 立即查询一次，页面可见期间每 2 秒查询；`onHide`、`onUnload` 或终态停止。
- 微信好友分享使用 `onShareAppMessage`。
- 海报由前端 Canvas 合成商品主图、金额、文案和服务端小程序码，不在服务端生成整张海报。
- H5 开发环境使用复制链接及 mock 支付；微信小程序环境使用真实分享和支付。

当前确认订单、订单列表和拼团等自付入口只创建支付单并跳转结果页，尚未真正调用 `uni.requestPayment`。实施支付驱动时必须提供一个小程序支付调起函数，并接入所有普通订单自付入口；拼团仍使用自付，但不开放代付分享。否则启用微信驱动后原有自付也无法完成。

结果页按查看人区分动作：

- 订单购买人支付成功：沿用现有成功落地页并保留“去预约”。
- 代付好友支付成功：显示“已帮好友完成付款”，仅提供“完成/返回”。
- 支付取消或失败：允许在支付尝试已明确失败或关闭后重试。

## 11. 安全与日志

- 分享令牌、Authorization、微信回调密文、签名头、私钥和 API v3 密钥不得进入日志。
- 当前请求日志中可能记录完整 Authorization 和请求体，实施微信回调前必须增加脱敏或排除规则。
- 公开预览与状态查询限流；支付创建必须登录。
- 所有金额只信任数据库订单和微信已验签结果，不接收客户端金额。
- 回调和主动查询共用同一个幂等结果应用函数，避免两套状态转换。

## 12. 实施顺序

1. 支付表结构和服务改造成多次尝试，保持现有自付与 mock 流程通过。
2. 微信支付驱动、回调、查单、关单、退款与补偿。
3. 代付分享接口和小程序支付页。
4. 小程序分享卡、海报和轮询体验。
5. 全链路资金异常演练后再启用生产配置。

## 13. 验收与测试

服务端至少覆盖：

- 订单购买人与实际付款人正确分离。
- 同一付款人重复创建复用支付；不同付款人并发只有一个进入支付中。
- 支付成功回调重复到达不重复完成订单。
- 自付与代付并发时最多一笔完成订单。
- 超时支付查单和关单成功后才允许新尝试。
- 迟到的额外成功支付自动生成退款并可补偿。
- 订单退款定位 `paid_payment_id` 并原路退还实际付款人。
- 额外支付退款不改变正常订单状态。
- 微信外部调用期间不持有数据库事务或行锁。
- 本地未保存 `prepay_id` 的宕机窗口可以通过查单、关单恢复。
- 公开预览和状态接口不泄露隐私。

微信驱动使用官方报文样例测试签名、验签、AES-GCM 解密、金额不一致和重复通知。小程序执行类型检查、H5 与微信小程序构建，并分别验证购买人和代付好友的结果页动作。
