# 我的预约、取消与改期设计

- 日期：2026-09-02
- 涉及项目：`yueji-backend`、`../yueji-web`、`../yueji-oss`
- 状态：已确认

## 1. 背景与目标

现有预约功能已经支持：

- 面诊预约与订单预约两种场景。
- 订单预约关联整笔已付款订单。
- 公开查询动态时段、统一时段容量和并发满额保护。
- 管理端分页、月历、容量配置及预约场景展示。

本次在现有预约模块上补齐“我的预约”生命周期：

- 待预约：已下单并付款，但尚未预约时间。
- 待到店：已经预约时间，尚未完成服务。
- 服务记录：已经完成的预约服务。
- 用户取消预约与改期。
- 客服后台代取消、代改期，以及面诊预约的人工完成。
- 小程序、服务端和管理端使用同一状态口径。

本项目仍处于开发阶段。现有预约数据仅用于联调，不做历史状态推断或兼容迁移；实施增量 SQL 时直接清理现有预约测试数据，再按新模型重新造数。订单、会员、商品、支付等其他业务数据不清理。

## 2. 已确认的业务决策

1. 订单预约取消后，订单本身不取消、不退款，并重新进入“待预约”，允许再次选择时间。
2. 用户可在预约开始前取消或改期；到达预约时间后不再显示自助按钮，由后台处理。
3. 订单预约在订单核销成功时自动完成；面诊预约由后台人工确认完成。
4. 取消原因不强制。小程序提供常用原因和可选备注，后台详情展示最终原因。
5. 后台支持客服代取消、代改期，并记录管理员、时间、原因和前后时间。
6. 小程序保留“已取消”列表，但个人中心仍只展示待预约、待到店、服务记录三个统计入口。
7. 底部 TabBar 的“预约”进入“我的预约”管理页，不再直接进入创建预约页。
8. 所有“去预约”入口在当前页面从底部拉起统一预约抽屉；改期复用同一个抽屉。
9. 个人中心三个统计入口切换到“预约”TabBar 页面，并自动选中对应状态。

## 3. 方案选择

采用“订单状态与预约状态分离、列表由服务端聚合”的方案。

- “待预约”不是预约记录状态，而是动态查询“已付款且没有非取消订单预约”的订单。
- 预约表只保存真实预约记录的 `BOOKED`、`COMPLETED`、`CANCELLED`。
- 小程序和后台都由预约模块返回统一列表项，不在页面自行拼接订单与预约状态。

不采用以下方案：

- 下单后预创建无日期的预约记录：会让预约表包含未实际发生的记录，并加重支付与预约耦合。
- 完全按订单状态和时间推算：无法可靠表达面诊完成、取消、改期和操作审计。

## 4. 领域状态与规则

### 4.1 状态定义

服务端新增预约状态常量：

```ts
export const AppointmentStatus = {
  BOOKED: 0,
  COMPLETED: 1,
  CANCELLED: 2,
} as const;
```

小程序列表使用四个展示 Tab：

```ts
export type AppointmentTab =
  | "PENDING_BOOKING"
  | "PENDING_ARRIVAL"
  | "SERVICE_RECORD"
  | "CANCELLED";
```

对应关系：

| 展示 Tab | 数据来源 | 是否占时段容量 |
| --- | --- | --- |
| `PENDING_BOOKING` | 本人 `PAID` 订单，且不存在 `BOOKED` 或 `COMPLETED` 的订单预约 | 否 |
| `PENDING_ARRIVAL` | `appointment.status = BOOKED` | 是 |
| `SERVICE_RECORD` | `appointment.status = COMPLETED` | 否 |
| `CANCELLED` | `appointment.status = CANCELLED` | 否 |

面诊预约创建后直接进入 `BOOKED`，不经过“待预约”。“待预约”只表示尚未选时间的订单服务。

### 4.2 创建

- 继续复用 `POST /api/v1/app/appointments`。
- 不带 `orderId` 时创建面诊预约；带 `orderId` 时创建订单预约。
- 订单必须属于当前会员且状态为 `PAID`。
- 同一订单允许存在多条历史取消记录，但最多只能存在一条非取消记录。
- 创建成功写一条 `CREATE` 操作日志。

### 4.3 取消

- 用户只能取消本人 `BOOKED` 且尚未开始的预约。
- 后台可取消任意仍为 `BOOKED` 的预约；如果预约已到点，确认框显示额外警告。
- 取消只修改预约，不修改订单、支付或退款状态。
- 订单预约取消后因只剩取消记录，订单自动重新满足“待预约”查询条件。
- 重复取消返回当前取消结果，不重复写日志。

### 4.4 改期

- 用户只能改期本人 `BOOKED` 且尚未开始的预约。
- 后台可为任意仍为 `BOOKED` 的预约改期；如果预约已到点，确认框显示额外警告。
- 改期不创建新预约，不改变状态，只更新当前记录的日期和时间并写 `RESCHEDULE` 日志。
- 新时间必须晚于当前时间、属于固定开放时段且仍有容量。
- 改期失败时原日期、时间和容量占用保持不变。

### 4.5 完成

- 订单预约只能由订单核销流程完成，预约后台不提供第二个“完成”入口。
- 面诊预约由后台点击“完成服务”，且预约时间必须已经开始。
- 完成后状态改为 `COMPLETED`，写入完成时间和 `COMPLETE` 日志。
- 已完成和已取消都是终态。
- 到点但尚未核销或人工完成的预约继续保持 `BOOKED`；本次不自动完成，也不增加爽约状态。

### 4.6 订单联动

- 订单核销在现有订单事务内，把该订单的 `BOOKED` 预约改为 `COMPLETED`，并记录核销管理员。
- 订单退款成功在现有退款事务内，把该订单的 `BOOKED` 预约幂等改为 `CANCELLED`，原因记录为“订单退款”。
- 没有关联预约时，核销和退款流程保持原行为。
- 取消预约绝不反向取消订单或发起退款。

## 5. 数据模型与开发期迁移

### 5.1 `appointment` 扩展

在现有预约表增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | `tinyint` 非空，默认 `0` | `0-BOOKED`、`1-COMPLETED`、`2-CANCELLED` |
| `complete_time` | `datetime` 可空 | 完成时间 |
| `cancel_time` | `datetime` 可空 | 取消时间 |
| `cancel_reason` | `varchar(255)` 可空 | 用户、客服或系统取消原因 |

保留现有会员、日期、时间、场景和订单关联字段。

### 5.2 有效记录唯一约束

删除现有：

- `uk_member_appointment_time(member_id, appointment_date, appointment_time)`
- `uk_appointment_order_id(order_id)`

改为 MySQL 生成列唯一索引：

- `active_order_id`：仅当订单预约状态为 `BOOKED` 或 `COMPLETED` 且未软删时返回 `order_id`，否则为 `NULL`；唯一索引保证同一订单最多一条非取消记录。
- `booked_member_slot_key`：仅当状态为 `BOOKED` 且未软删时，由会员、日期、时间拼接生成，否则为 `NULL`；唯一索引保证同一会员不会重复占用同一有效时段。

MySQL 唯一索引允许多个 `NULL`，因此可以同时保留多条取消历史，并允许订单重新预约。

新增查询索引：

- `(member_id, status, appointment_date, appointment_time)`
- `(status, appointment_date, appointment_time)`
- `(order_id, status)`

所有时段容量查询只统计 `status = BOOKED AND is_deleted = 0`。

### 5.3 操作日志

新增不可编辑的 `appointment_operation_log`：

| 字段 | 说明 |
| --- | --- |
| `appointment_id` | 预约 ID |
| `action` | `CREATE`、`RESCHEDULE`、`CANCEL`、`COMPLETE` |
| `operator_type` | `MEMBER`、`ADMIN`、`SYSTEM` |
| `operator_id` | 会员或管理员 ID；系统操作为空 |
| `before_date/time` | 操作前日期和时间，可空 |
| `after_date/time` | 操作后日期和时间，可空 |
| `reason` | 取消、改期或系统联动原因，可空 |
| `create_time` | 操作发生时间 |

日志只追加，不提供更新和删除接口。

### 5.4 SQL 策略

- 新增 `sql/mysql/appointment_lifecycle.sql`，明确标注为开发期破坏性迁移。
- 脚本只清理 `appointment` 及其操作日志数据，不触碰订单、支付、会员、商品等表。
- 清理后修改索引和字段，再重新生成符合新状态模型的测试预约数据。
- 同步更新 `sql/mysql/biz_phase6.sql`，保证新数据库直接得到最终表结构。
- 同步更新 `sql/mysql/biz_test_seed.sql`，覆盖面诊、订单、待到店、已完成、已取消和改期日志。
- 不编写历史回填或状态推断 SQL。

## 6. 服务端接口

### 6.1 C 端读取接口

#### 统计

`GET /api/v1/app/appointments/summary`

```json
{
  "pendingBooking": 2,
  "pendingArrival": 1,
  "serviceRecord": 4
}
```

只返回个人中心需要的三个数字，不返回已取消数量。

#### 我的预约分页

`GET /api/v1/app/appointments/page`

参数：

- `tab`：四个 `AppointmentTab` 之一，必填。
- `pageNum`、`pageSize`：沿用项目分页约定。

服务端按 Tab 执行对应查询，不建立额外通用查询框架。返回沿用 `{ data, page }`：

```json
{
  "data": [
    {
      "appointmentId": "12",
      "orderId": "18",
      "orderNo": "YJ202609020018",
      "sceneType": "ORDER",
      "status": 0,
      "appointmentDate": "2026-09-08",
      "appointmentTime": "14:00",
      "productNames": ["超光子嫩肤"],
      "canBook": false,
      "canCancel": true,
      "canReschedule": true
    }
  ],
  "page": { "pageNum": 1, "pageSize": 10, "total": 1 }
}
```

`PENDING_BOOKING` 项没有 `appointmentId`、日期和时间，固定为订单场景，并返回 `canBook: true`。其他 Tab 返回真实预约记录。按钮能力由服务端返回，页面不根据时间或状态自行猜测。

### 6.2 C 端动作接口

#### 取消

`POST /api/v1/app/appointments/:id/cancel`

```json
{ "reason": "行程有变；备注：下周再约" }
```

`reason` 可空，最长 255 字。会员 ID 只取 JWT。

#### 改期

`PUT /api/v1/app/appointments/:id/reschedule`

```json
{
  "appointmentDate": "2026-09-10",
  "appointmentTime": "16:00"
}
```

日期和时间复用现有创建 DTO 的格式与固定时段校验。

### 6.3 B 端接口

扩展现有接口：

- `GET /api/v1/appointments/summary`：全局四项统计。
- `GET /api/v1/appointments/page`：增加 `tab`、`sceneType`、日期范围、订单号和会员关键字筛选。
- `GET /api/v1/appointments/calendar`：默认只统计 `BOOKED` 容量，日详情可返回其他状态。
- `GET /api/v1/appointments/slots`：后台改期读取动态时段，复用同一 Service。
- `GET /api/v1/appointments/:id`：预约详情与操作日志。
- `PUT /api/v1/appointments/:id/reschedule`：客服改期。
- `POST /api/v1/appointments/:id/cancel`：客服取消。
- `POST /api/v1/appointments/:id/complete`：仅完成面诊预约。

“待预约订单”由分页接口的 `PENDING_BOOKING` 分支返回，只读展示并可跳转订单详情，不在预约后台代用户创建预约。

新增权限：

- `biz:appointment:reschedule`
- `biz:appointment:cancel`
- `biz:appointment:complete`

继续复用已有 `biz:appointment:query` 和 `biz:appointment:config`。

## 7. 服务端事务与并发

### 7.1 创建与重新预约

1. 校验会员、订单、日期和固定时段。
2. 锁定预约容量配置行。
3. 查询订单是否已有 `BOOKED` 或 `COMPLETED` 预约。
4. 仅统计目标时段的 `BOOKED` 数量。
5. 保存新预约并写 `CREATE` 日志。
6. 生成列唯一索引兜底并发重复。

历史 `CANCELLED` 记录不阻止创建新记录。

### 7.2 改期

1. 锁定目标预约，校验归属和 `BOOKED` 状态。
2. C 端校验当前时间早于原预约时间；B 端允许越过该限制，但显示警告。
3. 锁定容量配置行。
4. 统计新时段的其他 `BOOKED` 预约，排除当前预约。
5. 容量可用时更新日期时间并写一条 `RESCHEDULE` 日志。

任一步骤失败都回滚，原时间保持不变。

### 7.3 取消与完成

- 取消锁定预约后做状态条件更新；已经取消时幂等返回，不重复写日志。
- 面诊完成锁定预约并校验预约已开始，再更新状态和日志。
- 订单核销、退款通过当前事务的 `EntityManager` 同步更新预约和日志，避免订单成功但预约未联动。

## 8. 小程序设计

### 8.1 TabBar 页面

`../yueji-web/src/pages/appointment/index.vue` 从“创建预约”改为“我的预约”：

- 四个 Tab：待预约、待到店、服务记录、已取消。
- 待预约卡片：订单场景、订单号、商品摘要、查看订单、去预约。
- 待到店卡片：场景、订单摘要、预约时间、取消预约、改期。
- 服务记录卡片：场景、完成时间、订单或预约详情，只读。
- 已取消卡片：原预约时间、取消时间和原因；订单取消记录可再次从“待预约”进入预约。
- 每个 Tab 独立分页、加载态、错误态和空态。
- `onShow` 刷新统计和当前列表，保证从其他页面预约成功后数据同步。

未登录时显示登录引导，不请求会员接口；登录回跳后恢复目标 Tab。

### 8.2 统一预约抽屉

把现有预约页的日期、动态时段、订单资格和提交逻辑提取到 `YjAppointmentDrawer`：

```ts
type AppointmentDrawerMode = "create" | "reschedule";

interface AppointmentDrawerProps {
  visible: boolean;
  mode: AppointmentDrawerMode;
  orderId?: string;
  appointmentId?: string;
}
```

- 使用项目已安装的底部 Popup 能力，不增加依赖。
- 抽屉最大高度适配 H5 和微信小程序，内容区滚动，确认按钮固定在底部安全区上方。
- 层级高于自定义 TabBar。
- 创建订单预约时展示订单号和商品摘要；面诊预约不展示订单区块。
- 改期时展示原预约时间，只允许选择新时间。
- 关闭抽屉不丢失当前业务页面。
- 请求失败保持抽屉、原预约和当前选择；时段满额时刷新时段。
- 成功后发出 `success` 事件并关闭。

在“我的预约”页创建成功后，刷新统计并切到“待到店”。其他页面创建成功后保留当前页面，提示成功并提供“查看我的预约”入口。

### 8.3 抽屉入口

以下入口挂载并打开同一个抽屉组件：

- 首页“免费预约面诊”：不传 `orderId`。
- 支付结果“去预约”：传当前订单 ID。
- 已付款订单卡片“预约到店”：传订单 ID。
- “我的预约”待预约卡片“去预约”：传订单 ID。
- “我的预约”待到店卡片“改期”：传预约 ID 与 `reschedule` 模式。

入口点击时先走现有统一登录导航。登录成功返回原页面后，通过一次性参数重新打开抽屉，不新增全局事件总线或预约 Store。

### 8.4 个人中心与导航

- 个人中心调用 `summary`，替换三个固定 Mock 数字。
- 点击统计项时切换到 `RoutePath.APPOINTMENT`，用现有 TabBar 一次性参数传递目标 Tab。
- 预约页面读取并清除参数，选中对应 Tab。
- 删除重复的 `MY_APPOINTMENT` 占位路由和页面注册，避免两套“我的预约”。

### 8.5 订单列表能力

订单 C 端分页和详情补充最小预约摘要：

```ts
appointment?: { id: string; status: number } | null;
canBookAppointment: boolean;
```

只有服务端返回 `canBookAppointment: true` 时显示“预约到店”。点击后抽屉仍调用订单资格接口和创建接口做最终校验。

## 9. 管理端设计

扩展 `../yueji-oss/src/views/appointment/index.vue`，保留现有容量配置、分页和月历。

### 9.1 页面结构

- 顶部四项统计：待预约订单、待到店、服务记录、已取消；点击后切换筛选。
- 筛选：会员昵称/手机号、状态、场景、预约日期范围、订单号。
- `PENDING_BOOKING` 时禁用预约日期筛选，因为该类数据尚无预约日期。
- 表格增加状态、最近变更和操作列。
- 默认进入“待到店”，并默认查看当天，适合作为到店运营工作台。

### 9.2 操作

- 详情抽屉展示会员、场景、订单、当前时间、取消原因和完整操作时间线。
- 改期弹层读取后台动态时段，展示原时间，成功后刷新统计、列表和月历。
- 取消使用二次确认，原因和备注可选；越过预约时间时显示额外警告。
- “完成服务”只出现在已经开始的面诊预约。
- 订单预约提供“查看订单”，核销仍在订单管理完成。

### 9.3 月历

- 日期角标只统计 `BOOKED`，准确反映占用容量。
- 点击日期可查看当天全部状态记录，并用状态标签区分。
- 取消、改期、完成后同步刷新当月数据。

## 10. 错误处理

- 新时段满额：服务端拒绝；前端保持抽屉打开并重新读取时段。
- 订单状态或预约状态已变化：提示服务端消息，并刷新统计、列表或详情。
- 网络失败：不清空改期前的原时间，不假定操作成功。
- 非本人预约或订单统一返回“预约不存在”或“订单不可预约”，不泄露他人数据。
- 统计加载失败：个人中心显示 `—`，预约页保留重试入口，不使用旧 Mock 数字。
- 重复取消、核销和退款联动保持幂等。
- 所有状态、计数和按钮能力以服务端返回为准。

## 11. 测试与验收

### 11.1 服务端自动测试

在现有预约与订单测试基础上覆盖：

1. 已付款且无非取消预约的订单进入待预约；已预约、已完成和已退款订单不进入。
2. 创建面诊和订单预约后进入待到店，并正确占用容量。
3. 用户只能操作本人、未开始的 `BOOKED` 预约。
4. 取消后释放容量、保留历史、订单重新进入待预约并可再次预约。
5. 改期成功只更新当前记录并写前后时间；新时段满额时原预约不变。
6. 并发创建和并发改期由事务锁与唯一索引阻止超额和重复。
7. 订单核销自动完成订单预约；退款自动取消待到店预约；重复调用不重复写日志。
8. 后台只能人工完成已经开始的面诊预约。
9. Summary、四类分页、后台筛选和月历只使用正确状态口径。

运行后端 Jest 和生产构建。

## 13. 明确不做

- 不增加医生、门店、排班、独立号源或多门店容量。
- 不增加爽约状态、自动完成、预约提醒或消息通知。
- 不增加取消手续费、退款联动或提前 24 小时等可配置规则。
- 不允许后台在“待预约订单”中未经用户确认直接占用时段。
- 不新建预约 Store、全局事件总线、状态机框架或第三方抽屉依赖。
- 不兼容或回填现有预约测试数据；实施时只清理预约域测试记录。

## 14. 完成标准

用户从任意预约入口都能在当前页面完成面诊或订单预约；底部“预约”和个人中心统计进入统一“我的预约”页面。用户可以在开始前取消或改期，订单取消预约后可重新预约。后台可以查看四类数据、完整操作时间线、代取消、代改期并完成面诊服务；订单核销与退款会原子联动预约状态。三端统计、列表、月历和操作按钮始终使用服务端同一口径。
