# 阶段 0–5 审查问题修复设计

日期：2026-08-18

## 1. 背景与目标

后台前端、后台服务端和小程序由不同模型分阶段实现，当前主要风险不是代码风格不一致，而是同一业务规则在不同阶段、不同端出现了语义偏差。

本轮不做全项目重构。目标是按风险顺序修复已经由代码和需求对照确认的问题，并用最小闭环测试证明关键业务链路仍成立：

1. 先修复会影响部署、安全、权限和数据完整性的阻断问题。
2. 再统一商品、订单、会员、优惠券在前后端的业务口径。
3. 最后处理管理端和小程序的高优先级交互一致性问题。

不新增框架或基础设施；优先复用现有 NestJS、TypeORM、Vue、Taro 和数据库能力。

## 2. 方案比较

### 方案 A：一次性重构三仓库

同时重排模块、抽象公共层、统一 DTO 和页面结构。表面上统一程度最高，但改动面过大，难以区分原有缺陷和重构引入的回归，也不符合当前“先审查、再判断”的目标。

结论：不采用。

### 方案 B：按风险分批修复

保留现有模块边界，只在共同入口或业务根因处修复；每批都有明确验收项和最小测试。需求定义不完整的功能不实现，单独保留为后续业务确认项。

结论：采用。

### 方案 C：先补齐所有需求清单功能

优先补标签筛选、购买权限、批量核销等可见功能，但部署、权限和库存回补仍可能破坏生产数据。

结论：不采用。

## 3. 实施边界

涉及三个独立仓库：

- `yueji-backend`：配置、鉴权、权限、商品与订单生命周期、会员与优惠券校验、测试。
- `yueji-oss`：权限按钮、营销页面已确认的交互一致性。
- `yueji-web`：登录接口对齐、商品列表请求竞争。

本轮明确不做：

- 不改变现有数据库主键、订单状态值、金额单位或历史数据结构。
- 不引入新的事件总线、任务调度库、搜索组件或缓存层。
- 不实现尚无业务定义的商品“购买权限”。
- 不实现核销撤销、批量核销和核销操作日志；这些会改变财务及审计语义，需要单独定义权限、可撤销时限和补偿规则。
- 不为阶段 3 之后仍标记为占位的全部小程序页面补功能。
- 不提前重构真实微信支付事务；该项在接入真实支付驱动前单独设计。

## 4. 分批设计

### 批次 1：部署配置与秘密管理

#### 4.1 运行时配置

容器不再依赖镜像内复制的环境文件。Docker 镜像只打包程序，运行时由 Compose、部署平台或进程环境注入变量。

生产环境启动时执行现有配置校验并满足以下规则：

- 生产环境不得启用模拟登录。
- 生产环境不得使用模拟支付驱动。
- 必需的数据库、Redis、JWT、对象存储配置缺失时直接启动失败。
- 环境名称只接受项目约定值，避免文件名为 `prod`、实际值却为 `dev`。

#### 4.2 秘密文件

已追踪的真实环境文件从 Git 索引移除并加入忽略规则，只保留无凭据的示例文件。实施时保留开发者本地文件内容，不覆盖当前 `.env.dev` 修改。

仓库历史中出现过的对象存储密钥必须由维护者在云平台轮换；代码只能移除暴露源，无法让旧密钥自动失效。

#### 4.3 数据库初始化

Compose 仅在空数据卷首次初始化时，按固定顺序挂载当前阶段所需 SQL：基础库、业务基础表、商品菜单、订单菜单、会员菜单、阶段 4 表、阶段 5 表、营销菜单。

现有数据库仍按版本说明手工执行增量 SQL。不会把带建表或初始化数据的脚本伪装成可重复迁移，以免误伤已有数据。

验收：

- 新空数据卷启动后具备阶段 0–5 的表和菜单。
- 镜像中不包含 `.env*` 和真实密钥。
- 生产配置使用模拟登录或模拟支付时启动失败。

### 批次 2：鉴权与商品权限

#### 4.4 会员鉴权

JWT 和 Redis Token 两种守卫统一遵守公开接口与会员接口元数据，避免切换会话模式后公开接口被误拦截。

通过会员鉴权后查询会员当前状态；禁用会员即使持有尚未过期的 Token，也不能继续访问受保护接口。状态判断放在鉴权边界，不由每个业务控制器重复实现。

微信手机号换取接口改为官方要求的 JSON `POST` 请求，授权码不再出现在 URL 查询参数中。

模拟登录默认关闭，只有非生产环境且显式开启时可用。

现有刷新 Token 没有对应的小程序刷新接口。本轮不扩展刷新协议；小程序继续以重新静默登录处理过期会话，避免维护一套无人调用的接口。

#### 4.5 商品管理权限

商品与商品分类控制器增加与现有权限体系一致的细粒度权限：查询、新增、修改、删除、上下架。菜单 SQL 增加对应按钮权限，管理端按钮使用相同权限标识控制显示。

权限标识只定义一次清单，并逐层保持完全一致，不新增另一套角色模型。

验收：

- Redis Token 模式下公开接口、会员接口和后台接口的放行规则与 JWT 模式一致。
- 禁用会员的旧 Token 被拒绝。
- 微信手机号请求的方法和请求体符合接口约定。
- 无商品修改权限的管理员无法通过页面或直接调用接口修改商品。

### 批次 3：商品与订单库存闭环

#### 4.6 上架校验

商品状态为上架时，至少存在一个启用且未删除的 SKU。管理端输入校验提供即时提示，服务端承担最终校验；不能仅依赖页面。

#### 4.7 删除规则

只要商品或 SKU 被未终结订单引用，就禁止删除商品或从商品中移除该 SKU。未终结订单明确为：待支付、已支付、已核销。

已取消、已完成、已退款订单只保留历史快照，不阻止软删除。商品下架和 SKU 停用不等于删除，仍允许后续取消或退款回补实际 SKU 库存。

#### 4.8 库存聚合

订单取消或退款回补 SKU 后，不再直接给商品总库存加同一增量；改为从当前启用、未删除 SKU 重新汇总商品可售库存。这样已停用 SKU 的回补库存不会错误地重新成为前台可售库存。

现有事务和行锁继续保留，不新增库存服务层。

验收：

- 有待支付、已支付或已核销订单引用时，商品/SKU 删除被明确拒绝。
- 商品或 SKU 停用后，取消/退款仍可回补 SKU，订单能进入正确终态。
- 商品展示库存始终等于启用且未删除 SKU 的库存合计。
- 上架商品不会出现零个可售 SKU 的状态。

### 批次 4：会员、优惠券与管理端一致性

#### 4.9 有效会员等级

订单计价、会员账户页和会员 360 视图使用同一口径：已分配等级仍启用时采用该等级；等级被禁用时，根据现有累计消费规则解析有效等级。只统一查询结果，不批量改写会员历史等级字段。

#### 4.10 优惠券作用域

保存限定分类或限定商品的优惠券时，服务端校验目标记录存在且可作为当前业务对象引用。无效 ID 直接拒绝，不把错误留到下单阶段。

#### 4.11 管理端营销页面

只补已被后端支持但页面缺失的能力：

- 积分页增加时间范围筛选。
- 优惠券发行后允许延长有效结束时间，其他已锁定字段继续不可编辑。
- 发券结果同时展示成功数和跳过数。

超过 100 条数据的远程搜索选择器暂不实现；当前接口和实际数据量未证明需要新增分页交互，达到上限后再补。

验收：

- 等级禁用后，订单价格、账户页和 360 视图显示一致。
- 无效优惠券作用域不能保存。
- 管理端筛选和编辑规则与后端能力一致，批量发券结果不再隐藏跳过数量。

### 批次 5：小程序高优先级对齐

#### 4.12 登录接口

小程序 API 层改用现有后端 `/app/auth/*` 和 `/app/member/profile` 接口。登录成功后先保存访问令牌，再请求会员资料并映射到现有前端用户状态；不要求后端为单个客户端扩展重复响应结构。

#### 4.13 商品列表请求竞争

筛选或分页请求增加递增请求序号。新筛选发起后，旧响应即使晚到也被丢弃；加载锁不再导致用户的最新筛选被静默忽略。只在商品列表数据层修复，不引入请求取消库或全局状态框架。

验收：

- 小程序登录、获取手机号、拉取会员资料的 URL 和响应映射与后端一致。
- 快速切换分类、排序或刷新时，只展示最后一次筛选条件对应的数据。

## 5. 错误处理与兼容性

- 所有新增业务拒绝使用现有统一异常格式，前端展示服务端可读消息。
- 数据完整性规则由后端强制执行；前端校验只用于体验。
- 不改变已有成功响应外壳、Token 格式和订单状态枚举。
- SQL 初始化调整只影响新空数据卷；现有环境升级步骤在部署说明中列出。
- 删除商品/SKU 的新限制属于收紧规则，不迁移或删除历史订单。

## 6. 验证策略

### 后端

保留现有测试，并新增最小闭环覆盖：

1. 创建订单后取消：库存、积分、优惠券全部释放。
2. 支付后退款：订单终态、库存、积分、优惠券一致。
3. 使用优惠券和积分完成订单：金额与权益结算只执行一次。
4. 商品权限：无权限被拒绝，有权限可操作。
5. 禁用会员：旧 Token 不能访问，页面采用有效等级口径。
6. 活跃订单引用的商品/SKU 不能删除，停用 SKU 仍可完成回补。

运行现有单元测试、类型检查和与改动文件相关的 lint。

### 管理端

运行类型检查和相关页面 lint；手工验证按钮权限、优惠券编辑限制、发券结果与积分时间筛选。

### 小程序

使用项目要求的 pnpm 9 安装依赖后运行类型检查；手工模拟慢响应，验证旧商品请求不会覆盖新筛选结果。

## 7. 提交与回滚

每个批次独立提交，三仓库不混合无关改动。现有本地环境文件和锁文件修改不纳入提交。

推荐提交顺序：

1. 后端配置与数据库初始化。
2. 后端鉴权和商品权限，随后同步管理端权限。
3. 后端商品/订单库存闭环及测试。
4. 后端会员/优惠券与管理端营销页面。
5. 小程序登录和商品列表。

每批均可通过回退对应提交恢复代码。数据库批次不删除已有数据；若生产启动校验阻止部署，应先补齐正确配置，不通过放宽校验绕过。

## 8. 后续单独决策项

以下内容保留为新需求，不混入本轮缺陷修复：

- 商品购买权限的主体、范围、默认策略和下单拒绝规则。
- 核销撤销的权限、时限、审计记录及权益补偿。
- 批量核销的部分失败语义和幂等规则。
- 真实微信支付调用与本地事务之间的状态机、回调和对账补偿。
- 多实例部署后的分布式定时任务归属。

这些规则确认后再设计最小实现，避免现在为未知需求搭建抽象层。
