# 预约场景关联设计

## 1. 背景与目标

现有预约服务已经具备固定时段、统一容量和并发满额保护；小程序也已有预约页面，但仍使用静态时间列表，未读取服务端时段状态。业务还需要区分两类预约：

- 面诊预约：会员直接从预约入口提交，不关联订单。
- 订单预约：会员支付成功后针对整笔订单预约到店。

本次交付同时完成服务端、小程序和管理端接入：预约成功时保存场景及订单关联，后台能看到场景、订单号和订单内全部商品名称。

## 2. 已有实现与复用范围

- 复用现有 `appointment` 表、预约创建接口、配置行事务锁和容量统计，不另建预约场景表。
- 复用现有订单详情接口与订单商品快照，不复制订单号或商品名称到预约表。
- 复用小程序现有预约页、支付结果页和订单卡片；不新建第二套订单预约页面。
- 保留现有“同一会员、同一天、同一时间”唯一约束；两种场景共同占用同一时段容量。

## 3. 业务规则

- `CONSULTATION` 表示面诊预约，`order_id` 为空。
- `ORDER` 表示订单预约，`order_id` 必须存在。
- 请求携带 `orderId` 时由服务端判定为订单预约；未携带时判定为面诊预约，客户端不能自行提交场景类型。
- 订单预约只允许当前登录会员自己的订单，且订单状态必须为 `1`（已支付/待核销）。
- 一笔订单最多预约一次；预约关联整笔订单，后台展示订单号及该订单全部商品名称。
- 两种场景均只能选择服务端返回的 `10:00` 至 `18:00` 固定时段，并共同参与容量统计。
- 既有预约统一视为面诊预约。

## 4. 数据模型与增量 SQL

在 `appointment` 表增加：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `scene_type` | varchar(20) | 非空，默认 `CONSULTATION` | `CONSULTATION` 或 `ORDER` |
| `order_id` | bigint | 可空，唯一索引 | 订单预约关联的业务订单 ID |

增量 SQL 为已有记录回填 `CONSULTATION`，并增加 `uk_appointment_order_id(order_id)`。MySQL 唯一索引允许多条 `NULL`，因此可直接保证“一笔订单最多预约一次”，无需额外场景表或 JSON 字段。

## 5. 服务端接口与事务

### 5.1 时段查询

`GET /api/v1/app/appointments/slots?appointmentDate=YYYY-MM-DD` 改为公开接口，未登录用户也能查看时段；接口继续返回每个时段的容量、剩余数量、满额和可用状态。

### 5.2 创建预约

`POST /api/v1/app/appointments` 继续要求会员登录，请求体增加可选字段：

```json
{
  "appointmentDate": "2026-09-03",
  "appointmentTime": "14:00",
  "orderId": 123
}
```

创建事务按以下顺序处理：

1. 校验日期、固定时间段和过去时间。
2. 锁定预约配置行，沿用现有容量并发保护。
3. 若有 `orderId`，读取订单并校验会员归属及状态 `1`；通过后写入 `ORDER` 和订单 ID。
4. 若无 `orderId`，写入 `CONSULTATION`，订单 ID 为空。
5. 统计该日期和时间的全部预约，满额则拒绝；写入时继续由数据库唯一索引兜底重复会员时段和重复订单。

接口响应补充 `sceneType` 与 `orderId`。重复订单统一返回“该订单已预约”；订单不存在或不属于当前会员时返回“订单不可预约”；订单状态不符时返回“当前订单状态不可预约”。

### 5.3 订单预约资格

新增会员接口 `GET /api/v1/app/appointments/order-eligibility?orderId=123`，返回 `{ eligible, reason }`。服务端检查订单归属、状态及是否已有预约；不存在或非本人统一视为不可预约，不泄露他人订单信息。该接口只用于页面预先禁用和提示，创建接口仍执行相同校验并作为最终依据。

## 6. 管理端展示

预约分页和日历数据补充：

- `sceneType`
- `orderId`
- `orderNo`
- `productNames`

服务端先获取预约结果，再批量读取本页或当前日历范围内涉及的订单及订单项并装配字段，避免关联订单项导致分页重复，也避免逐条查询。

管理端列表和日历展示“面诊预约”或“订单预约”。订单预约额外展示订单号和全部商品名称；面诊预约不显示空的订单信息。现有筛选、容量配置和日历交互保持不变。

## 7. 小程序流程

- 普通预约入口进入 `/pages/appointment/index`，按面诊预约提交。
- 支付成功页“去预约”携带 `orderId` 跳转预约页。
- 状态为 `1` 的订单卡片显示“预约到店”，携带 `orderId` 跳转预约页。
- 预约页存在 `orderId` 时并行读取现有订单详情和订单预约资格，展示订单号和商品名称；订单不存在、非本人、状态不符或已经预约时，展示服务端错误并禁用提交。
- 预约页按日期调用时段接口，以 `available` 控制按钮禁用状态，以 `full` 展示满额；不再维护静态 `10:00` 至 `19:00` 列表。
- 日期变化和预约成功后重新读取时段，提交时把 `orderId` 原样传给服务端。
- 未登录跳转登录后保留预约页及 `orderId` 查询参数。
- 首页和个人中心仍指向旧预约占位页的入口统一改到现有预约页。

为避免快速切换日期时旧请求覆盖新日期，只接收当前日期对应的最新时段响应；不引入额外状态库或请求依赖。

## 8. 异常与并发

- 前端禁用只改善交互，订单权限、订单状态、容量和重复预约均以服务端校验为准。
- 订单在进入页面后发生状态变化时，提交接口再次校验并拒绝。
- 多次点击或并发请求由订单唯一索引阻止重复订单预约。
- 两种场景竞争最后一个名额时，继续由预约配置行写锁保证只有一条成功。
- 列表装配不到已删除或异常订单资料时仍返回预约记录，订单展示字段为空，不影响后台查询。

## 9. 明确不做

- 不增加取消、改期、预约状态、医生、门店或排班。
- 不按订单商品拆分多条预约。
- 不保存订单号和商品名快照，不新增场景扩展表。
- 不改造当前订单详情占位页面；订单预约入口直接复用预约页。

## 10. 验证与完成标准

最小服务端测试覆盖：

- 未带订单可创建面诊预约。
- 当前会员状态为 `1` 的订单可创建订单预约并保存场景。
- 非本人订单、非状态 `1` 订单和重复订单被拒绝。
- 订单预约资格接口对上述三类订单返回不可预约。
- 面诊与订单预约共同占用时段容量。
- 时段查询无需会员登录。

管理端执行类型检查和生产构建；小程序执行类型检查及 H5/微信小程序构建，并在浏览器验证动态时段、面诊提交、订单信息展示和无效订单禁用。完成后，后台列表和日历均能区分两种场景，并显示订单预约对应的订单号及全部商品名称。
