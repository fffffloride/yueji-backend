# 订单送礼技术设计

- 日期：2026-09-03
- 涉及项目：`yueji-backend`、`../yueji-web`
- 状态：已确认

## 1. 目标与范围

为普通已购买订单增加整单转赠能力：购买人创建分享，好友登录后领取服务权益，双方可查看转赠记录。分享和受赠视图不展示金额。

本次只转移预约、核销等服务使用权，不转移购买记录、付款记录、积分、优惠券、分销或退款资金归属。

首期明确不做：

- 拆分订单项或数量转赠。
- 受赠人再次转赠。
- 拼团订单转赠。
- 已预约、已核销、已完成或退款中的订单转赠。
- 消息通知、定时发送和管理端转赠运营页。

## 2. 已确认规则

1. 仅支持整单转赠。
2. 原订单购买人与付款账务永久保留，只转移服务权益。
3. 赠礼领取后，购买人可以查看原订单和转赠记录，但不能预约或核销。
4. 赠礼链接有效期为 7 天；领取前购买人可撤回。
5. 领取后不能直接退款。未预约、未核销时，受赠人可先退回，购买人再联系客服并由后台按现有流程退款。
6. 退款原路退给原支付账户。
7. 分享预览及受赠人的订单视图均隐藏金额。

## 3. 方案选择

采用“订单购买人与当前权益人分离”的方案：

- `biz_order.member_id` 继续表示原购买人，现有支付、营销、积分和分销逻辑保持不变。
- `biz_order.beneficiary_member_id` 表示当前有权预约、核销服务的会员。
- `biz_order_gift` 记录转赠状态和审计信息。
- 订单状态仍走 `UNPAID → PAID → VERIFIED → COMPLETED/REFUNDED`，不增加“已赠送”状态。

不采用直接修改 `member_id`：该字段已被支付、退款、优惠券、积分、累计消费和分销结算使用，修改会污染历史账务。

不建设独立权益资产系统：当前只支持整单一次性服务权益，单独资产层没有实际收益。

## 4. 状态机

```text
创建分享
   ↓
PENDING ──购买人撤回──→ REVOKED
   │
   ├──超过 7 天──→ EXPIRED
   │
   └──好友领取──→ CLAIMED ──受赠人退回──→ RETURNED
```

约束：

- `PENDING` 只影响分享，不改变订单权益人。
- `CLAIMED` 时才把订单权益人改为受赠人。
- `RETURNED` 时把权益人恢复为原购买人。
- 过期采用惰性更新：预览、领取、列表或再次创建分享时发现超时即改为 `EXPIRED`，不增加定时任务。
- 同一订单同一时刻最多一条 `PENDING` 记录。

## 5. 数据模型

### 5.1 `biz_order`

新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `beneficiary_member_id` | `bigint` 非空 | 当前服务权益人 |

迁移时把历史数据回填为 `member_id`；普通订单和拼团订单创建时均同时写入两个会员字段。

增量迁移按“先增加可空列 → 回填并校验空值 → 改为非空”的顺序执行，并同步全量建表脚本与测试种子。

新增权益人查询索引：

- `(beneficiary_member_id, is_deleted, create_time, id)`

### 5.2 `biz_order_gift`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `order_id` | `bigint` | 订单 ID |
| `sender_member_id` | `bigint` | 原购买人 |
| `recipient_member_id` | `bigint` 可空 | 实际领取人 |
| `token_hash` | `char(64)` | 分享令牌 SHA-256，不保存明文 |
| `status` | `tinyint` | `0-PENDING`、`1-CLAIMED`、`2-REVOKED`、`3-EXPIRED`、`4-RETURNED` |
| `expires_at` | `datetime` | 领取截止时间 |
| `claimed_at` | `datetime` 可空 | 领取时间 |
| `revoked_at` | `datetime` 可空 | 撤回时间 |
| `returned_at` | `datetime` 可空 | 退回时间 |

索引与约束：

- `token_hash` 唯一。
- 生成列 `pending_order_id = CASE WHEN status = 0 AND is_deleted = 0 THEN order_id END`，增加唯一索引，保证每个订单最多一个待领取分享。
- `(sender_member_id, status, create_time, id)`。
- `(recipient_member_id, status, create_time, id)`。
- 状态和软删除字段增加检查约束。
- `beneficiary_member_id`、订单 ID、发送人和领取人增加与现有订单/会员表一致的外键约束。

分享令牌使用 Node.js `randomBytes(32).toString("base64url")` 生成，服务端收到明文后立即计算 SHA-256 查询。

## 6. 资格与权限

创建转赠必须同时满足：

- 请求人是 `order.member_id`，且仍是 `order.beneficiary_member_id`。
- 订单状态为 `PAID`。
- 不存在 `BOOKED` 或 `COMPLETED` 的有效订单预约，统一复用现有 `ACTIVE_ORDER_APPOINTMENT_STATUSES` 口径。
- 不存在处理中的退款。
- `group_buy_member` 中不存在该订单。

领取必须登录，领取人只从会员 JWT 获取，不能由客户端传入。领取时再次校验全部条件，并拒绝购买人领取自己的礼物。

订单读取权限：

- 购买人始终可查看原始订单的金额、支付与转赠记录，但当前权益人不是本人时绝不返回核销码。
- 当前权益人可查看脱敏订单、预约与核销信息，但不返回金额、购买人联系方式和营销抵扣明细。
- 只有当前权益人可以获得当前核销码。接口直接返回 `viewerRole`、`canGift`、`canBookAppointment`、`canReturnGift` 等能力字段，页面不自行推断。

## 7. 核心事务

### 7.1 创建分享

1. 写锁订单。
2. 惰性关闭已过期的 `PENDING` 记录。
3. 校验订单、预约、拼团和退款条件。
4. 若仍有有效 `PENDING`，返回“已有待领取赠礼”；不保存可恢复的明文令牌。
5. 生成新令牌并保存摘要，返回一次明文令牌和 7 天到期时间。

页面保留本次返回的令牌用于微信分享。再次进入页面时若令牌已丢失，购买人可撤回旧分享后重新生成。

### 7.2 领取

1. 事务外按令牌摘要找到候选记录。
2. 事务内按固定顺序先写锁订单，再写锁赠礼记录。
3. 重新校验状态、到期时间、订单状态、当前权益人、预约和退款。
4. 写入领取人和领取时间，把赠礼改为 `CLAIMED`。
5. 把 `beneficiary_member_id` 改为领取人。
6. 重新生成唯一核销码，使购买人此前保存的旧码立即失效。

同一领取人重复提交返回已有领取结果；另一会员竞争领取时统一返回“礼物已被领取或失效”，不泄露领取人信息。

### 7.3 撤回、过期与退回

- 撤回：购买人只能撤回自己的 `PENDING` 赠礼，不改权益人。
- 过期：把超时的 `PENDING` 改为 `EXPIRED`，不改权益人。
- 退回：当前受赠人在订单仍为 `PAID`、没有 `BOOKED` 或 `COMPLETED` 有效预约且没有退款时操作；写锁订单和赠礼，把权益人恢复为购买人、状态改为 `RETURNED`，并再次更换核销码。

### 7.4 退款与履约联动

- 后台创建退款前若权益人不是购买人，则拒绝并提示先退回赠礼；本次不新增会员自助退款申请系统。
- 退款进入 `PROCESSING` 后领取与退回均被拒绝。只有退款成功落库的事务才把尚未领取的赠礼改为 `REVOKED`；退款失败后原分享仍可领取。
- 预约资格、待预约列表和核销权限全部以 `beneficiary_member_id` 为准。
- 积分、优惠券、累计消费、分销和退款继续以 `member_id` 及原支付记录为准。

现有扫码核销存在“事务外按码查单、锁单后不再核对原码”的时间窗口。实施时必须让内部核销函数接收期望核销码，并在取得订单写锁后再次比较；按订单 ID 核销可不传期望码。否则领取或退回刚更换的旧码仍可能在并发中完成核销。

## 8. 服务端接口

统一前缀 `/api/v1`：

| 方法 | 路径 | 鉴权 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/app/order-gifts` | 会员 | 创建分享 |
| `POST` | `/app/order-gifts/preview` | 公开、限流 | 按令牌读取安全预览 |
| `POST` | `/app/order-gifts/claim` | 会员 | 领取 |
| `POST` | `/app/order-gifts/:id/revoke` | 会员 | 撤回 |
| `POST` | `/app/order-gifts/:id/return` | 会员 | 退回 |
| `GET` | `/app/order-gifts` | 会员 | 按 `SENT/RECEIVED` 分页查询记录 |

令牌放请求体，避免后端 API URL 和访问日志直接记录令牌。小程序分享页使用 `?token=` 接收后立即用于请求，不写入本地持久化存储。

公开预览只返回：商品名称、主图、规格、数量、赠送人昵称、过期时间和当前可领取状态。

## 9. 小程序改造

- 复用 `YjOrderCard` 增加“赠送好友”，按钮能力完全读取服务端。
- 实现现有 `/pages-sub/order/gift/index` 页面，支持创建分享、好友领取、送出记录和收到记录。
- 领取成功后复用现有订单预约抽屉，不建立第二套预约页。
- 我的订单查询同时包含本人购买订单和本人当前受赠订单，并按 `viewerRole` 隐藏金额与动作。
- 使用 `onShareAppMessage` 分享小程序路径；分享标题、图片和页面快照都不含金额。
- H5 环境提供复制链接作为开发和兜底能力。

## 10. 安全与日志

- 公开预览限流，错误统一为“礼物不存在或已失效”。
- 不记录分享令牌、会员 JWT、微信回调密文或完整手机号。
- 核销、领取、退回都由订单写锁串行化，不增加分布式锁。
- 领取、退回等核心一致性操作必须在单个数据库事务内完成，不依赖异步事件最终一致。

## 11. 验收与测试

服务端至少覆盖：

- 可赠与不可赠资格组合。
- 多人并发领取仅一人成功。
- 同一人重复领取幂等。
- 领取与预约、退款、核销竞争时只有合法操作成功。
- 领取和退回后旧核销码失效。
- 扫码查询旧码与领取/退回并发时，锁内二次校验必须拒绝旧码。
- 已领取订单必须退回后才能退款。
- 公开预览及受赠订单不返回金额和隐私字段。
- 过期、撤回、退回后不能再领取。

多人领取以及领取与核销、退款的竞争需要在真实 MySQL 上执行集成检查，不能只依赖 mock repository 单测。小程序执行类型检查及 H5、微信小程序构建，并人工验证分享、领取、记录、退回和预约入口。
